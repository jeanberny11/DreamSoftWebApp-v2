## Conventions
<!-- Naming rules, file patterns, coding styles specific to this project -->
[2025-05-25] Page file names: `<Feature>Page.tsx` (PascalCase + Page suffix). Component file names: `<Name>.tsx` (PascalCase). CSS file names: `<name>.css` (kebab-case).
[2025-05-25] Feature file names follow the pattern `<feature>.<role>.ts` — e.g. `login.slice.ts`, `login.state.ts`, `login.types.ts`, `login.api.ts`.
[2026-06-19] `stores/` folder is used in both `landingapp` and `tenant`. `store/` (singular) is no longer used — all slices and Zustand stores live in `stores/` within their feature folder.
[2025-05-25] Redux slice export for reset action: `reset<Feature>` — e.g. `resetLogin`, `resetRegister`.
[2025-05-25] Redux thunks receive `t()` as an argument in the ThunkArg interface so slices stay i18n-aware.
[2025-05-25] State pattern mirrors flutter_bloc: discriminated union with `status: 'initial' | 'loading' | 'success' | 'error'`.
[2025-05-25] Always use `@/` path alias for imports that cross feature/app boundaries. Never use `../../` across app boundaries.
[2025-05-25] i18n default and fallback language is Spanish (`es`). Keys must always be added to both `en/` and `es/` simultaneously.
[2026-07-16] `tenant-control-panel` stores are called directly from pages/components with fetch triggered in a local `useEffect` (see `SubscriptionsSection.tsx`) — no wrapper hook layer, unlike `home` (which wraps every store in a hook, e.g. `usePricing()`).
[2026-07-16] New reusable UI built for `tenant-control-panel` (e.g. `NewSubscriptionPlanCard`) must be its own component, not a reused `home` component — even visually similar ones like `PricingCard` — since TCP renders icons as Material Symbols ligature text while `home` maps icon codes through FontAwesome via `getFeatureIcon()`.

[2026-07-22] Guard architecture: guards are COMPOSABLE via nested layout routes — each guard checks one condition and renders `<Outlet />` or redirects. New guards `EmailVerifiedGuard` (checks `session.emailVerified`) and `ProfileCompleteGuard` (checks `session.onboardingCompleted` — which maps to backend `Tenant.OnboardingCompleted` = profile setup ONLY, not full onboarding; verified in `GetOnboardingChecklistQueryHandler.cs`) both live in `common/guards/` and redirect to `/account` (dashboard checklist shows the pending step) when their condition fails; deep-link `from` is deliberately dropped in that case. Currently gating `subscriptions/new` + `subscriptions/new/checkout` inside the `/account` layout in `routes.tsx`; nest them around any future route that needs these conditions (they assume LandingAuthGuard is an ancestor).
[2026-07-22] Auth round-trip: `LandingAuthGuard` passes `state={{from: pathname+search}}` to `/login` (search matters — checkout deep-link params live in the query string); BOTH `LandingGuestGuard` and `useLogin` must honor `state.from` (the guard would otherwise race the hook's success-effect and win); login navigates with `replace:true`. Register intentionally does NOT round-trip (user decision — fresh accounts are unverified and can't subscribe).
[2026-07-22] Plan-change proration: Stripe only resets billing/charges when a trial explicitly starts or ends via an EXPLICIT trial_end change (confirmed via Stripe docs). Therefore the change-plan flow (preview AND commit) deliberately NEVER sends a TrialEnd/trial_end parameter — omitting it preserves any remaining trial days on the subscription untouched. This is the entire mechanism for "switched plan keeps remaining trial days, no fresh trial, no reset-by-switching abuse" — no other special-casing needed. Preview-to-commit exactness: `ProrationDate` is captured once by the gateway's `PreviewPlanChangeAsync` (UTC now at preview time), returned in the response, and MUST be echoed back on the real `ChangePlanCommand.ProrationDate` — this pins the actual Stripe charge to match the previewed number exactly (Stripe's own recommendation). `GetChangePlanPreviewQueryHandler`'s validation steps are a deliberate 1:1 mirror of `ChangePlanCommandHandler`'s — keep them in sync if either changes, or a successful preview could lead to a rejected confirm.
[2026-07-22] UX research for manage/cancel/change (pt.6, web-sourced): be exact about money (precise next charge/date, preview consequences before commit); cancellation must be findable, clearly labeled, minimal steps, surveys OPTIONAL/after (dark patterns → -28% trust, -54% usability; click-to-cancel regulation); tell users exactly what happens post-cancel (access-until date prominent; immediate cancel must state NO REFUND); plan changes must "show the math" (compact proration preview "$X today, $Y on {date}", upgrades charge prorated now, downgrades credit/next-cycle).
